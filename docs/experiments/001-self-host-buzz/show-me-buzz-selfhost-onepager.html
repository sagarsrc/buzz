L0 → L2: layer-by-layer path

Treat this as staged adoption, not one abstract “self-hosting” bucket. Each layer adds ops burden, infra shape, and honesty requirements.

L0
evaluate in minutes
  • Use Railway one-click path or local `just setup && just relay`.
  • Goal: prove product model — relay as workspace, signed events, shared human/agent surface.
  • Good for founder validation, not production proof.
  • Do not confuse root `docker-compose.yml` with production path — repo marks it dev-only.
L1
single VPS / core offering
  • Use `deploy/compose/` bundle with Postgres, Redis, MinIO, git volume, optional Caddy TLS.
  • Best current commercial framing: one customer team, one community, one stack.
  • Desktop app is primary full UX; CLI/ACP are strong supporting surfaces.
  • Pin image tag. Keep secrets stable. Back up all stateful pieces.
L2
helm / managed infra / HA
  • Use `deploy/charts/buzz/` with external Postgres, Redis, and S3.
  • Production Helm path expects `secrets.existingSecret` and GitOps discipline.
  • HA requires Redis; chart supports autoscaling and race-safe auto-migrations.
  • Use when team wants managed services, GitOps, or multi-replica posture.

What is required to self-host Buzz

Current Buzz is not “just run one binary.” Real runtime dependencies are explicit in repo docs and deploy manifests.

Infra / services

  • Buzz relay image (`ghcr.io/block/buzz:<tag>`)
  • PostgreSQL
  • Redis
  • S3-compatible object store / bundled MinIO
  • Persistent git storage
  • Domain + TLS termination

Secrets / identity

  • `BUZZ_RELAY_PRIVATE_KEY`
  • `RELAY_OWNER_PUBKEY`
  • `BUZZ_GIT_HOOK_HMAC_SECRET`
  • Postgres credentials
  • Redis password
  • S3 / MinIO credentials

Operational actions

  • Pin immutable image tag (`sha-...` or semver), not `:main`
  • Run migrations (`BUZZ_AUTO_MIGRATE=true` or `buzz-admin migrate`)
  • Provision members/invites via `buzz-admin` + relay flows
  • Back up DB + object store + git data + secrets + owner key

Compose L1 shape

deploy/compose/ compose.yml compose.caddy.yml .env.example run.sh

Single-node/VPS bundle. Optional Caddy TLS. Compose v2.24.4+ required.

Recommended path

  • L0: eval locally / Railway to validate product fit.
  • L1: launch first self-host offer on one VPS per team.
  • L2: move to Helm only when managed services / HA / GitOps become hard requirement.
  • Be explicit that desktop is primary interface today.

Why L1 first

  • Fastest route to real customer deployment.
  • Least engineering beyond repo’s current supported path.
  • Keeps failure domains simple: one stack, one team, one domain.
  • Avoids overselling multi-community and browser parity too early.

Agentic customization surfaces

If multi-agent services are core offering, strongest customization is not infra. It is the agent layer: which agents exist, what they can do, how they are routed, what tools they get, what memory they keep, and which workflows they automate.

Roles
what agents exist
  • Persona packs define named agents / teams per client.
  • Each persona can carry its own system prompt, MCP config, and skill set.
  • Good fit for client-specific roles like research, triage, reviewer, release, docs, incident, support.
Routing
when agents engage
  • BUZZ_ACP_* controls subscription mode, channel scope, mention handling, allowlists, and respond-to rules.
  • Agents can be scoped per channel, per workflow, or per event type.
  • Client offering can decide whether agents are reactive assistants, background workers, or both.
Capability
what agents can do
  • Tool surface comes from MCP sidecars, buzz-cli, and persona pack config.
  • Capabilities can include messaging, workflow control, repo operations, canvas, memory, and relay actions.
  • This is where client differentiation is highest without forking core product.

Agent surfaces available for customization

SurfaceWhat can vary per client
Persona layer Agent names, role definitions, prompts, MCP config, packaged skills, team composition
Model layer Provider, model, effort level, turn timeout, token caps, heartbeat, memory on/off
Routing layer Mentions vs all events, channel filters, allowlists, owner-only vs anyone, config rules
Workflow layer Trigger rules, webhook integrations, approval steps, YAML automations, escalation paths
Tooling layer MCP sidecars, shell/file tools, repo policy commands, CLI surfaces exposed to agents
Core feature layer New event kinds, new agent protocol behavior, new relay features — this becomes fork work

What is easy vs expensive

  • Easy — custom personas, prompts, models, channel routing, allowlists, seed workflows, memory defaults.
  • Medium — client-specific tool bundles, MCP sidecars, tighter workflow orchestration, operator/admin runbooks around agent usage.
  • Hard — new native agent capabilities, new relay event kinds, deep admin/auth changes, product forks.

Rule: if customization stays in persona packs, ACP config, workflows, and MCP composition, it is still productized. Once it needs new kinds or relay behavior, it is a fork.

Known blockers, gaps, operator burden

These are not hypothetical caveats. They are directly reflected in repo docs and should be presented with the same prominence as strengths.

Product / platform gaps

  • Workflow approval gates not wired end-to-end.
  • `send_dm` and `set_channel_topic` workflow actions are stubbed.
  • Web is not full workspace client.
  • Mobile is still maturing.

Security / ops gaps

  • No real rate limiting implementation yet.
  • Compose defaults to mutable `:main` image tag.
  • No clear LTS support model; security support centers on active `main`.
  • Backup/restore story exists as checklist, not polished runbook.

Scope boundaries

  • Do not frame current offer as compliance-grade or enterprise-ready.
  • Do not promise multi-tenant productization from day one.
  • Do not promise minimal-mode single-binary deployment — Redis + S3 are real deps today.

Sovereignty tradeoffs

  • Operator owns infra, TLS, backups, upgrades.
  • Key loss is identity loss — no recovery softness.
  • Onboarding friction exists because Nostr keys are real, not hidden behind OAuth magic.

Founder takeaway

If question is “can we offer Buzz self-hosted now?”, answer is yes. If question is “what version of that offer is honest today?”, answer is L1 Compose on a VPS for a technical team.

What not to overclaim

Do not pitch current repo as browser-first collaboration suite, polished multi-tenant hosted platform, or compliance-grade enterprise control plane. Pitch it as sovereign, technical, real, and early.
